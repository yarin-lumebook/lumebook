01
Language + IDE — Where you write code
Required · Free
Swift
Required Free
The programming language
Apple's official language for building Mac and iOS apps. Think of it as the instructions you write that the computer executes. Every Mac app is written in Swift (or the older Objective-C). Swift is readable and modern — a `for` loop looks like: for item in items { doSomething(item) }. You're not learning a niche language — Swift is in the top 15 most-used languages globally.
Gotcha: Swift updates every year alongside Xcode. Code written in Swift 5 may need minor changes to compile in Swift 6. This is the "language treadmill" — not a crisis, but real overhead.
Xcode
Required Free
IDE — Integrated Development Environment
The single tool where you write code, design UI, run your app, debug errors, profile performance, and submit to the App Store. Think of it as Photoshop for apps — one program that does everything. It's 10–15GB, slow to open, and crashes more than it should. All of that is normal. Every Mac developer uses it.
Cost: Free (requires macOS + Apple account to download)
Gotcha: Xcode only runs on Mac. No exceptions. Also: updating Xcode mid-project can break your build. Treat Xcode updates like OS updates — wait 2 weeks for others to report issues first.
SwiftUI
Built into Xcode Free
UI Framework — builds what users see
SwiftUI is Apple's modern way to build your app's visual interface. You describe what you want — SwiftUI figures out how to render it. Example: Text("Hello").font(.title).foregroundColor(.blue) shows blue title text. No drag-and-drop required, though Xcode has a visual Preview panel. SwiftUI is the right choice for new apps in 2025.
Gotcha: SwiftUI still has holes — some advanced Mac features require dropping down to AppKit (the older framework). You'll hit this around month 3 when you need something SwiftUI can't do yet. Plan for it.
AppKit
Built into Xcode Advanced
Older UI Framework — for Mac-specific power features
AppKit is the original Mac UI framework, predating SwiftUI by 20+ years. You'll need it when SwiftUI can't do what you need — custom window behaviors, menu bar apps, system tray icons, complex drag-and-drop. Most apps use SwiftUI as the base and call AppKit for specific things. It's not a separate tool — it lives alongside SwiftUI in the same Xcode project.
How it connects: You write Swift code inside Xcode. Xcode compiles (translates) that code into a binary the Mac can run. SwiftUI code describes your UI; Xcode renders a live preview of it as you type. You don't install Swift separately — it comes with Xcode.
02
Dependency Management — Plugging in existing code
Required · Free
Swift Package Manager (SPM)
Use This Free
Modern dependency manager — built into Xcode
Apps don't get built from scratch. You "import" libraries — packages of code other developers wrote — so you don't reinvent wheels. SPM is how you do that in 2025. Need to make network requests? Import Alamofire. Need to render charts? Import Swift Charts. SPM is built directly into Xcode: File → Add Package Dependencies → paste a GitHub URL → done. It downloads the code, links it, and you can start using it.
Cost: Free. Built into Xcode.
Gotcha: Dependency conflicts — when two packages need different versions of the same thing — can cause build errors with cryptic messages. Resolution: delete the Package.resolved file and let SPM rebuild it.
CocoaPods
Legacy Free
Older dependency manager — still widely used
CocoaPods predates SPM and many older libraries still use it. You create a Podfile, list your dependencies, run pod install, and it creates a .xcworkspace file you must open instead of the normal project. For new projects, prefer SPM. You'll encounter CocoaPods when tutorials or libraries require it.
Gotcha: CocoaPods is installed via Ruby (already on your Mac). But after installing, if you open the wrong file (.xcodeproj instead of .xcworkspace), nothing works and you'll think it's broken. Always open the workspace file.
Swift Package Index
Free Reference
Directory of available packages
swiftpackageindex.com — the Google for Swift packages. Before building something from scratch, search here. Need push notifications? Crash reporting? In-app purchases? Keyboard shortcuts? There's almost certainly a package that solves it. The site shows compatibility, version history, and documentation quality — saving you from adopting a dead package.
How it connects: SPM lives inside Xcode. When you add a package, Xcode fetches the code from GitHub, builds it alongside your code, and makes it available via import PackageName at the top of any Swift file. The package versions are locked in Package.resolved — this is committed to Git so your collaborators get the exact same versions.
03
Data Storage — Where your app's data lives
Depends on your app · Free to $$$
SwiftData / Core Data
Built in Free
On-device database — data stored only on the user's Mac
If your app's data never needs to sync across devices or be shared between users, you don't need a server at all. SwiftData (2023+, modern) and Core Data (older) store data directly on the user's Mac — like a local database file. A note-taking app, a task manager for one person, a tool that processes local files — none of these need cloud backends. Most indie apps start here.
Cost: Free. Built into Apple frameworks.
Gotcha: SwiftData is powerful but still maturing. For multi-user sync or data that needs to be on multiple devices, you need CloudKit or an external backend on top of it.
CloudKit
Free tier Apple-native
Apple's cloud sync — free if targeting only Apple devices
CloudKit is Apple's backend storage that syncs data through iCloud. If your app is Mac/iPhone/iPad only and needs cross-device sync, CloudKit is the natural first choice — it's free for reasonable usage, deeply integrated with SwiftData/Core Data, and requires no server you manage. The free tier includes 100MB database, 10GB assets, and 2GB transfer/month per app. Data lives in the user's iCloud account.
Cost: Free up to generous limits. Apple handles all infrastructure.
Gotcha: CloudKit only works on Apple devices. If you ever want a web version or Android app, you'll need to migrate to a different backend — which is painful after you've built on it.
Supabase
Free tier Cross-platform
Open-source "backend as a service" — database + auth + storage
Supabase gives you a full backend without building one: a PostgreSQL database (SQL — like a spreadsheet on steroids), user authentication (sign up/log in), and file storage, all in one dashboard. Best choice if you need cross-platform or want SQL. The free tier is genuinely usable for indie apps. You call it from Swift via the Supabase Swift SDK.
Cost: Free up to 500MB database, 1GB storage. $25/mo after.
Firebase
Free tier Google
Google's backend — real-time data, auth, analytics
Firebase (by Google) is the most-used mobile backend globally. It uses Firestore — a NoSQL database that stores data as documents (think JSON) rather than tables. Best for real-time features (chat, live collaboration, live scores) or if you want battle-tested infrastructure. Heavily documented. Has a generous free tier. Downside: vendor lock-in to Google.
Cost: Free (Spark plan). Blaze plan scales on usage.
Gotcha: Firebase is opinionated about data structure. Relational data (users → orders → items) is harder to query in Firestore than in SQL. If your data is naturally relational, choose Supabase.
How it connects: Your Swift code calls the backend SDK (e.g., supabase.from("tasks").select()). The SDK makes HTTPS network requests to the backend's servers, which respond with JSON data. You parse that JSON back into Swift objects. For CloudKit, Apple's framework handles all of this automatically with minimal code.

Decision rule: App stores user data only on one Mac → SwiftData. Syncs across Apple devices → CloudKit. Needs web/Android or SQL → Supabase. Needs real-time sync or massive scale → Firebase.
04
Version Control — Saving your history
Required · Free
Git
Required Free
Version control system — tracks every change to your code
Git is the undo button for your entire project — but infinitely more powerful. Every time you "commit," Git takes a snapshot of all your code. You can revert to any past snapshot, try risky experiments in "branches" without touching your working code, and see exactly what changed between versions. Without Git, one wrong change can destroy weeks of work. It's already installed on your Mac (via Xcode Command Line Tools).
Gotcha: Git has its own vocabulary (commit, push, pull, branch, merge, rebase). The first week is confusing. Use the 5 core commands only: git add . → git commit -m "message" → git push. Don't try to learn everything at once.
GitHub
Free Use This
Cloud home for your code — backup + collaboration + automation
GitHub stores your Git history in the cloud (so your code isn't only on your laptop) and adds a web interface to browse it. Think of it as Dropbox for code, but smarter. It also provides GitHub Actions — free automation that can run your tests, build your app, and send it to TestFlight on every code push. For solo developers, the free tier covers everything you need.
Cost: Free for public repos, free for private repos (up to 3 collaborators).
SourceTree / GitKraken
Free Optional
Visual Git clients — Git without memorizing commands
If Terminal commands feel intimidating, SourceTree (free) and GitKraken (freemium) give you a visual interface to Git. You click buttons instead of typing commands. Xcode also has basic Git built in (Source Control menu) which handles the 90% case without any extra tool.
How it connects: You write code in Xcode → you commit that change via Git (either in Terminal or Xcode's Source Control menu) → you push to GitHub, which stores a copy in the cloud. Later, GitHub Actions can watch for those pushes and automatically trigger builds, tests, and deployments — no manual intervention.
05
Testing — Making sure it works
Required · Mostly Free
XCTest
Built into Xcode Free
Unit testing — testing individual functions in isolation
XCTest is Apple's testing framework, built into Xcode. You write "unit tests" — small pieces of code that check whether a specific function works correctly. Example: you have a function that converts Fahrenheit to Celsius — you write a test that asserts convert(32) == 0. Xcode runs all your tests with one button press (⌘U) and shows you which pass and which fail.
Simulator
Built into Xcode Free
Virtual Mac/iPhone on your Mac — test without real devices
Xcode includes simulators — virtual devices that run inside your Mac. You can run your app on a simulated iPhone 15, iPad, or different Mac screen sizes without owning those devices. For Mac apps, you run them directly on your Mac. Simulator is your primary testing environment during development.
Gotcha: Some things only work on real devices, not simulators — push notifications, certain sensors, in-app purchases in production mode, and some camera features.
TestFlight
Required for beta Free
Apple's beta testing platform — distribute to real users before launch
Before publishing to the App Store, you distribute your app to testers via TestFlight. You upload your app to Apple's servers, invite testers by email, and they install it on their real devices. TestFlight handles versioning, tester management, and crash collection. Up to 10,000 external beta testers per app. This is how you get real-world feedback before launch.
Gotcha: TestFlight builds require the same code signing setup as real App Store submissions. Setting up code signing correctly is one of the most frustrating parts of the whole pipeline — budget a full day for it.
Instruments
Built into Xcode Free
Profiling — find memory leaks and performance bottlenecks
Instruments is Xcode's performance analysis tool. It records exactly what your app is doing: CPU usage, memory, network, battery. When your app runs slowly or crashes mysteriously after 30 minutes of use, Instruments is how you find out why. It's like a medical scanner for your app. You won't need it immediately but you'll need it before you ship.
How it connects: Write code in Xcode → press ⌘U to run all XCTest tests → fix failures → run your app in the Simulator to test UI manually → upload to TestFlight for real users to test on real devices → fix issues found → submit to App Store. Instruments runs at any point during this process when something feels slow.
06
Build Automation — Repeatable, hands-free releases
Optional early · Essential at scale
Fastlane
Free Intermediate
Automates build, sign, test, and deploy in one command
Fastlane is a command-line tool that automates everything you do manually before a release: increment the build number, run tests, sign the app, package it, upload to TestFlight, submit to the App Store, take screenshots. What takes 30 minutes of manual steps becomes one command: fastlane beta. It's installed via Ruby (bundler) and configured with a Fastfile in your project.
Gotcha: Fastlane setup involves touching certificates, provisioning profiles, and Apple IDs — the most confusing part of the whole stack. Use "Fastlane Match" (part of Fastlane) to manage certificates in a private GitHub repo. First setup: 2–4 hours. After that: magic.
GitHub Actions
Free Intermediate
Runs automation in the cloud on every code push
GitHub Actions is free CI/CD automation that runs on GitHub's servers. You write a .yml file describing steps — "when I push to main, build the app and upload to TestFlight." Every push triggers the pipeline automatically. macOS runner time is free for 2,000 minutes/month on GitHub Free. This is how professional teams ship without manual builds.
Cost: Free (2,000 macOS minutes/month). macOS runners cost 10× the base rate against your quota.
App Store Connect
Required to ship Free
Apple's web dashboard — manage submissions, pricing, metadata
appstoreconnect.apple.com is Apple's portal where you: create your app listing, upload builds for review, set pricing, write App Store descriptions, manage TestFlight testers, view sales reports and analytics, respond to reviews, and manage agreements. Every Mac App Store app has a page here. It's free to access but requires an Apple Developer account ($99/year).
How the full pipeline connects: You push code to GitHub → GitHub Actions starts a macOS runner → the runner runs fastlane beta → Fastlane builds the app (via xcodebuild), signs it (via Match certificates), and uploads to TestFlight (via App Store Connect API) → TestFlight notifies your testers → they install and test → you merge to release branch → GitHub Actions runs fastlane release → app submitted to App Store Connect → Apple reviews (1–3 days) → your app is live.
07
Post-Launch Infrastructure — Running blind vs. knowing
Strongly recommended · Free tiers available
Sentry
Free tier Recommended
Crash reporting — know when and why your app crashes
Without crash reporting, you only know your app crashes when a user emails you — which happens rarely, after they've already left a 1-star review. Sentry automatically captures every crash, sends you a report with the exact line of code that failed, the device model, OS version, and what the user was doing. You integrate it by adding the Sentry SDK via SPM and one initialization line.
Cost: Free up to 5K errors/month. $26/mo after.
PostHog / Mixpanel
Free tier Recommended
Product analytics — understand how users actually use your app
Analytics answer: which features do people actually use? Where do people drop off? What's the most common path through the app? Without this you're guessing. PostHog is open-source (can self-host, strong privacy story) and has a generous free tier. Mixpanel is more mature. Both integrate via Swift SDK. Each "event" you track is a line of code: posthog.capture("feature_used").
Gotcha: Every analytics SDK must be declared in your Privacy Manifest. Collecting data without user consent violates GDPR (EU), CCPA (California), and Apple's guidelines. Use anonymized IDs, not user emails, and offer opt-out.
RevenueCat
Free tier If monetizing
In-app purchase + subscription management
Apple's StoreKit API (for in-app purchases) is notoriously complex and has changed twice in recent years (StoreKit 2). RevenueCat is a layer on top that makes subscriptions and purchases manageable: it handles receipts, validates purchases server-side, tracks churn, shows revenue dashboards, and lets you A/B test paywalls. For a solo developer charging for an app, RevenueCat saves weeks of backend work.
Cost: Free up to $2.5K MRR. 1% of revenue after.
Sparkle
Free Required outside App Store
Auto-update framework — required if you distribute outside App Store
The App Store handles updates automatically. If you distribute your app directly (via your website), you need to build update delivery yourself. Sparkle is the open-source standard — it checks an "appcast XML" file you host, detects newer versions, and prompts users to update. Without it, users stay on old versions forever. Integration via SPM + 30 minutes of configuration.
How it connects: Sentry SDK → auto-reports crashes to your Sentry dashboard. Analytics SDK → you log events throughout your code, they appear in your analytics dashboard. RevenueCat → wraps StoreKit, syncs purchase status to their servers, available via Swift SDK. Sparkle → reads your hosted appcast XML file, prompts users when a new version exists.
