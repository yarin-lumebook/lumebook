01
Architecture · The decision you can't undo
App type isn't a style choice.
It's a different career.
The very first question — "how do I build this?" — has four completely different answers that each create a different cost structure, skill requirement, and user experience. No one tells you this upfront.
☠ Fatal if ignored
The four app types are four different worlds
There's native SwiftUI (best performance, Apple-native, hardest), Electron (JavaScript in a Chrome shell — 200MB download, cross-platform, but feels "off" on Mac), web app wrapped in a container (Tauri, fastest to build, lightest), and no-code tools (Draftbit, Glide — fast but severely limited). Each requires completely different skills. Choosing wrong at day 1 means starting over.
☠ Fatal if ignored
You need a Mac to build for Mac
Xcode — Apple's IDE (the tool where you write and build apps) — only runs on macOS. There is no Windows or Linux version. If you don't own a Mac, your first cost is hardware. Minimum viable Mac: ~$999. This is not optional for native development.
⚠ High impact
SwiftUI vs AppKit — even "Mac-native" has two paths
SwiftUI is Apple's newer, cleaner framework. AppKit is older and more powerful but lower-level. Most tutorials teach SwiftUI — but many pro features still require AppKit knowledge. You'll hit this wall around month 3 when you need something SwiftUI can't do yet.
⚠ High impact
Xcode is 10–15GB and frequently breaks itself
Apple's development tool is enormous, slow to download, and notoriously unstable. Crashes, corrupt indexes, build failures after minor updates are common. Many developers lose hours per week to tooling issues alone. This is normal and expected — not a sign you're doing something wrong.
◆ Medium impact
iOS and Mac apps are closer than you think
Since Apple Silicon (M1+), you can run iOS apps on Mac without modification. "Mac Catalyst" lets you port an iPad app to Mac with a checkbox. This changes the build order question: should you build for iPhone first, then expand? Many indie developers do exactly this.
◆ Medium impact
Git and version control aren't optional
Without version control (Git), one bad code change can destroy weeks of work with no recovery. You need to learn basic Git commands — or at minimum use Xcode's built-in source control — before writing your first real feature. This is infrastructure, not advanced skill.
Mental Model · First Principles
Think of app type like choosing between building a house from bricks, modular panels, a prefab, or Lego. You can get a livable result from all four — but each requires different tools, different trades, and has different long-term structural limits. The question isn't "which is better" but "which matches the thing I'm actually trying to build and the skills I actually have."
02
Apple's Rules · You're a tenant, not an owner
Apple is your landlord.
And they change the lease annually.
Most people think Apple's role ends at the App Store listing. In reality, Apple controls distribution, security checks, payment rails, annual API deprecations, and can remove your product from the market at any time with no recourse.
☠ Fatal if ignored
"Sherlocking" — Apple can make your app worthless overnight
At WWDC (Apple's annual developer conference), Apple announces OS features. Every year, they absorb 3–10 popular third-party apps into the OS itself — for free. Window managers (Rectangle), call recorders (TapeACall), password managers (1Password), writing tools (Grammarly) have all been partially or fully Sherlocked. You have no warning. No compensation. No appeal. Building something Apple "might" build is an existential risk.
☠ Fatal if ignored
Sandboxing can make your core feature impossible
Apps in the Mac App Store must run in a "sandbox" — a restricted zone that can't access other apps, system files, or network interfaces without explicit Apple permission. If your app idea requires reading other apps' data, monitoring system events, or accessing protected directories — the App Store may be the wrong distribution channel. Discovering this after 6 months of building is catastrophic.
⚠ High impact
The annual OS treadmill is a perpetual job
Apple ships a major macOS update every September. Each update can break existing APIs, deprecate features, change UI behaviors, or require Xcode upgrades. You're expected to update your app within months — or it may stop working, get flagged in App Store rankings, or get rejected on next submission. This is unpaid maintenance work that never ends.
⚠ High impact
App Store rejection can take 5–14 days per cycle
Apple reviews every app submission manually. Rejection reasons can be vague ("guideline 4.2 — minimum functionality"), and the appeal process is slow. A single rejection + fix + resubmit cycle costs 1–2 weeks. Multiple rejections can delay launch by months. The reviewer changes each time; you're not guaranteed consistency.
⚠ High impact
Apple's bureaucracy is legendary — and getting worse
App Store submissions now require: signed agreements (re-signed when Apple updates terms), tax forms, regional compliance, Digital Services Act public phone number and physical address, Privacy Manifest files for every third-party SDK, age ratings, encryption declarations. None of this is code. All of it takes time. All of it can block your launch.
◆ Medium impact
Developer certificates expire — and can break user installs
Your signing certificate has a validity window. If you sign an app outside the App Store with a certificate that later expires, users on older macOS may get warnings. Understanding the difference between Developer ID, Distribution certificates, and Notarization tickets is a non-trivial topic that blocks shipping.
Mental Model · 48 Laws of Power · Law 1
Never outshine the master — but here, the master can change what "outshining" means at any WWDC keynote. The correct move is to build in the spaces Apple has historically never touched, or build such deep user loyalty that Apple's native alternative feels like a downgrade (as Things 3 survived Reminders, Todoist survived Reminders, Halide survived Camera).
03
Distribution · Two paths, both expensive
Shipping ≠ distributing.
They're completely different problems.
The moment your app works on your machine, you've solved 40% of the problem. Getting it onto other people's machines is a separate engineering and legal challenge almost nobody accounts for in their timeline.
☠ Fatal if ignored
Without notarization, users see "app is damaged" and delete it
Since macOS Catalina, any app distributed outside the App Store that isn't notarized (Apple's security scan) triggers a Gatekeeper warning: "This app can't be opened because Apple cannot check it for malicious software." Most non-technical users interpret this as a virus warning and delete your app immediately. Notarization requires: a paid Developer account, Hardened Runtime enabled, code signing, uploading to Apple's servers, and stapling the result to your binary.
⚠ High impact
App Store = 30% tax. Outside = your own payment infra
The App Store handles payments but takes 30% (15% if under $1M revenue). Distributing directly via your website keeps 100% — but you now need to build: payment processing (Stripe, Paddle), license key generation and validation, piracy protection, refund handling, and VAT/tax compliance for every country you sell in. These are non-trivial engineering projects.
⚠ High impact
Auto-update is not free — you have to build it
The App Store handles updates. Outside of it, you're responsible for building an update delivery mechanism. The standard solution is Sparkle (an open-source framework) — but integrating it, signing updates, hosting the appcast XML file, and maintaining the update server is a separate project that takes 1–3 days minimum.
⚠ High impact
Crash reporting and analytics aren't built in
Without third-party SDKs, you're flying blind after launch. You won't know if 80% of users crash on startup, which features nobody uses, or where people drop off. Common tools: Sentry (crash reporting), Mixpanel or PostHog (analytics), TestFlight (beta testing — free but requires Apple account). Each SDK must be declared in your Privacy Manifest and reviewed by Apple.
◆ Medium impact
EU law now allows alt-stores but adds its own compliance layer
Since March 2024, the Digital Markets Act forced Apple to allow alternative app stores in the EU. AltStore PAL charges users €1.50/year and takes 0% commission. But participating requires additional notarization steps, marketplace agreements, and managing regional distribution separately.
◆ Medium impact
Your app icon needs 10 different sizes
Apple requires icons at: 16×16, 32×32, 64×64, 128×128, 256×256, 512×512, and 1024×1024px (plus @2x retina versions). Each must be crisp at its specific size — a design that looks great at 512px often becomes an unrecognizable blob at 16px. Icon design for Mac is a specialized skill.
Mental Model · Atomic Habits · Environment Design
Distribution is a friction problem. Every step between "user hears about your app" and "app is running on their Mac" is an opportunity to lose them. App Store: low friction for users, high cost + control for you. Direct: high friction setup for you, zero friction for users who trust you. Design distribution before you write line one of code.
04
Monetization · The math most people ignore
Paid apps are dying.
Subscriptions are hard.
Free apps cost you money.
Every pricing decision is a bet on user psychology, market positioning, and platform economics. The model you pick at launch is extremely hard to change — raising prices makes users angry; moving from free to paid kills momentum.
⚠ High impact
One-time paid apps now generate <5% of App Store revenue
The era of "pay $4.99, own forever" is essentially over. Subscriptions now dominate non-gaming revenue, growing 25% year-over-year through 2025. The problem: subscriptions require you to continuously justify your price — which means continuous new features, support, and marketing. A subscription app is never "done."
⚠ High impact
Subscription fatigue is real — the average user holds 6.7 active subscriptions
Users are increasingly resistant to adding more recurring charges. Your paywall must clearly answer "why is this worth $X/month on top of everything else I already pay?" in under 5 seconds. Without a compelling answer, conversion rates collapse. Trial-to-paid conversion below 25% signals a paywall or onboarding problem — not a pricing one.
⚠ High impact
Free apps don't mean free business — ads require massive scale
For an ad-supported Mac app to generate meaningful revenue (e.g., $2,000/month), you need hundreds of thousands of monthly active users. iOS CPM is ~$5; Mac is lower. Most indie apps never reach this scale. Free + ads is a trap that gives you the worst of both worlds: low revenue and a worse user experience.
◆ Medium impact
Pricing by region is a separate problem
A price that feels fair in the US ($9.99/month) may price out 90% of your potential users in India, Brazil, or Southeast Asia. Apple offers storefront pricing — you can set different prices per country — but deciding which markets to prioritize and at what price requires research most indie developers skip.
◆ Medium impact
Monetization must be designed before you build, not after
If you build a freemium app, the division between free and paid features must be designed into the app's architecture from day one. Retrofitting a paywall into an existing app is painful — it touches every screen, every user flow, and every API call. The monetization model is a product decision, not a business one.
● Tactical
Apple's "Small Business Program" cuts their cut to 15%
If your app earns under $1M/year through the App Store, you automatically qualify for Apple's Small Business Program — dropping their commission from 30% to 15%. For subscriptions beyond one year, it drops to 15% after year 1 anyway. This matters when calculating unit economics.
Mental Model · First Principles · Unit Economics
Before writing code, calculate: (price × conversion rate) − (Apple's cut + hosting + support time + annual maintenance cost) = actual revenue per user per year. Most indie apps generate negative revenue per user at launch because maintenance costs weren't accounted for. Know your number before you build.
05
Marketing · If you build it, they won't come
The Mac App Store has
1.9M+ apps. You are invisible
by default.
Discovery is the single biggest challenge indie developers cite. With no marketing budget and no existing audience, the odds of organic success are extremely low — and the levers that work are non-obvious.
⚠ High impact
ASO is the SEO of app stores — and most people skip it
70% of App Store visitors find apps through search. Your app's name, subtitle, keyword field (invisible to users), and first sentence of description are the primary ranking signals. Getting these wrong means ranking on page 47. Getting them right is a sustained research practice — you research what words your users search, optimize, wait 4–8 weeks, and iterate.
⚠ High impact
Launch day traffic vanishes in 48 hours
The App Store briefly boosts new apps in search rankings at launch. After 48–72 hours, you fall back to your "real" position determined by ratings, keyword relevance, and download velocity. Most indie apps launch, briefly appear in "New Apps," and then disappear into the void. Without pre-built audience or press coverage, launch day is often the peak.
⚠ High impact
Reviews are algorithmic signals, not just social proof
Apps rated below 4.0 effectively don't exist — 90% of users check ratings before downloading. The App Store algorithm also factors ratings into ranking. But you can't ask for reviews at random — you must use Apple's official SKStoreReviewRequest API, which only surfaces the prompt after positive in-app moments, and only 3 times per year.
◆ Medium impact
Screenshots are your actual landing page
Most users decide to download (or not) based entirely on screenshots — before reading a word of your description. Professional App Store screenshots are a distinct design discipline with specific canvas sizes (2880×1800 for Mac), compositional conventions, and A/B testing tools. Bad screenshots kill conversion from good search rankings.
◆ Medium impact
Being "Featured" by Apple is not a strategy
The Today tab and "Editors' Choice" are editorially curated by Apple. They do not follow a public criteria. There is no form to submit. Most featured apps have either an existing Apple relationship, a compelling new-platform story (e.g., first app for Apple Vision Pro), or incredibly polished design. Do not build your growth strategy around being featured.
● Tactical
In-App Events are an underused discovery channel
Apple's In-App Events let you publish time-limited event cards (challenges, launches, milestones) that appear in search results and the Today tab. In 2025, most apps still don't use them — making it a low-competition discovery lever. Events last up to 31 days and can be localized per country.
Mental Model · Distribution Before Product
The successful indie apps (CARROT Weather, Halide, Things 3) all had one thing in common before launch: an audience. Not a marketing plan — an audience. Reddit communities, Twitter followings, newsletter subscribers, people who explicitly said "I want this." Build the audience before the app. The app is the fulfillment of a promise, not the beginning of a pitch.
06
The Real Budget · What everyone forgets
The app costs money
to not build, not to build.
The hidden financial reality of Mac app development: costs that start before you write code and never stop after you ship. Most first-timers budget for building and run out before launching.
⚠ Ongoing cost
Maintenance = 15–20% of build cost, every year, forever
Once your app is live, you're committed to: fixing bugs users report, updating for annual macOS releases, maintaining compatibility with new Xcode versions, updating third-party SDKs, and renewing your developer account ($99/year). A "done" app that earns $500/month may cost $200/month in time to maintain. This is the math that kills indie businesses.
⚠ Ongoing cost
Hidden compliance costs after every third-party SDK update
Since 2024, Apple's Privacy Manifest requirement means every time a third-party SDK you use releases an update, you may need to update your own Privacy Manifest before your next submission. This turns routine updates into compliance audits. Miss one, and your app submission gets rejected with a vague error.
⚠ Ongoing cost
Customer support is a full-time job nobody budgets for
Users will email you. At scale, it's dozens per day. App Store reviews can't be directly responded to in a way that resolves issues. Negative reviews from unresolved support issues tank your rating faster than bugs do. Building a basic support system (help center, templated responses, Intercom or Crisp) is a product and cost center most solo developers ignore until it's too late.
◆ Upfront cost
The full pre-launch checklist nobody shows you
Before you can ship: privacy policy URL (required by Apple, can't be your Twitter), terms of service, age rating questionnaire, App Privacy Manifest, GDPR/CCPA considerations if you collect any data, App Store screenshots (multiple sizes), app preview video (optional but high-impact), localized metadata if targeting non-English markets. None of this is code. All of it gates launch.
◆ Upfront cost
What "building" actually costs at market rates
If you hire: simple apps start at $10–30K; mid-complexity at $50–100K; complex apps $100K+. If you learn and build yourself, the cost is time — typically 6–18 months for a first real app while learning Swift. With Claude Code and AI assistance, timelines are compressed but not eliminated. The hidden cost is opportunity cost: what else could you be doing with 12 months?
● Tactical
Localization multiplies both revenue and work
Adding a second language to your App Store listing can meaningfully increase downloads in non-English markets. But each language requires translated metadata ($200–500/language for professional translation), potentially localized screenshots, and ongoing maintenance of translated strings. The revenue uplift needs to justify the ongoing overhead.
Mental Model · Atomic Habits · True Cost Accounting
The true cost of an app isn't the build cost. It's (build cost) + (annual maintenance) × (years you plan to run it) + (opportunity cost of your time) + (Apple's cut of revenue) + (support infrastructure). Most business plans for indie apps skip items 2–5. Run the math for 5 years before committing. If it doesn't work on paper, it won't work in reality.
The three decisions that determine everything
Decision 1 · Before you build
App type
Native SwiftUI, Electron, Tauri, or no-code. Each is a different 12-month commitment. Choose based on what the app actually needs to do, not what tutorials make easy.
Decision 2 · Before you build
Distribution path
App Store (controlled, discoverable, 15–30% cut, sandboxed) or Direct (your own infra, full revenue, no restrictions). Decides what features are even possible.
Decision 3 · Before you build
Monetization model
Subscription, one-time, freemium, or B2B. Must be designed into app architecture from day one. Cannot be effectively retrofitted after launch.
